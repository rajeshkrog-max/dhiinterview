## Summary
Spec 0005: the server now scores at Finish (`checks.complete` -> `makeResult`) with the browser's own `score.js`, saves `results` plus a separate `resultFlags` row, exposes them only through the owner's `results.mine` / `results.ensure`, and every result page now draws from `DhiSession.result()` (device copy `dhirise.result.v1`, else `mine`, else `ensure`) behind a 10 second try again box. The server side is careful: one transaction, OCC makes concurrent `complete` / `ensure` safe, only the `score()` call is mapped to `scoring_failed`, the log carries only the check id, and the tests follow the ACs closely. The main problem is in the browser retry box: a timer that is never cancelled can put a permanent overlay over a page that has already drawn. The rest are smaller edge cases.

## Major

### 🟠 Retry timer can cover an already drawn page with a dead "could not load" box, `src/lib/session.ts:683`
**Problem**: Each `attempt()` starts its own 10 s `timer` that calls `resultBox(true, attempt)` without checking `settled`. Each timer is cleared only when *its own* `loadResult()` settles. Here is the sequence. Attempt 1 is slow, and the box shows at 10 s. The student taps Try again, so attempt 2 starts with timer 2. Attempt 1 then resolves: `settled = true`, the box is removed and the page draws. Attempt 2 is still in flight, and it can easily pass 10 s because `mine` has a 12 s cap, `ensure` has 15 s and `getClient` has 8 s. When timer 2 fires, it adds the full screen box (`position:fixed; inset:0; z-index:98`) over the drawn report. Its button calls `attempt()`, which returns at once because `settled` is true. When load 2 later settles, its handler returns early on `settled` and never removes the box. The student is stuck behind "We could not load your result" until they reload. The same happens if attempt 1's rejection arrives during attempt 2. In that case the box is shown, then removed when attempt 2 resolves, which is fine; only the stale timer case sticks.
**Why it matters**: This happens on slow mobile networks, the exact case the box was built for, and to students who tap Try again as told. The report, done page and story become unusable for that page view.
**Suggested fix**: Check `settled` inside the timer callback, and also inside the rejection handler. Better, keep a single current timer and generation counter in the closure: starting a new attempt clears the previous timer, and `settled` removes the box and clears any live timer. Add a unit or e2e test for this sequence: slow first attempt, tap Try again, first attempt resolves, second attempt hangs past 10 s.

## Minor

### 🟡 A finished check that can no longer be scored is locked out with a misleading "check your connection" message, `convex/resultsCore.ts:73` / `src/lib/session.ts:635`
**Problem**: `ensure` (and a repeated `complete`) refuse with `scoring_failed` when fewer than 18 answers score. That happens if an old check's option ids no longer exist in `questions.js`, or if an older row set is short. In the browser, `loadResult` treats every error except `not_completed` as transient, so the student gets the "check your connection and try again" box forever. Repeated `complete` calls on an already finished check also change behaviour: they used to return `completedAt` and can now throw.
**Why it matters**: Pre-release checks get `ensure` on first view (AC-7). One bad historical row means a permanent blank report and a wrong explanation. The only signal is a console line with the check id (no alert until scope row 9).
**Suggested fix**: In `loadResult`, give `scoring_failed` its own kind message (not a connection one). Consider counting `ensure` failures before launch, for example with a one off internal query that scores every finished check without a result in dry run, so data problems show before students hit them.

### 🟡 The device copy is trusted without a shape check, `src/lib/session.ts:606` (and `store.js` `result()`)
**Problem**: `readResultCopy` returns `copy.result` as soon as `v`, owner and `completedAt` match. A truncated, hand edited or future shaped copy (missing `areas`, `top`, ...) resolves the promise and makes `build(r)` throw inside a `.then`. The result is an unhandled rejection and a blank page with no box, because the promise has already resolved. The server path, by contrast, goes through `flatten`'s shape guard.
**Why it matters**: The device copy is the only path once it exists, so a bad copy breaks the page on every visit until sign out.
**Suggested fix**: Run the same minimal shape check `flatten` uses on the stored copy, and on failure drop the key and fall through to `mine`.

### 🟡 The scoring lock can be "updated" by editing the current version's fixture entry, `convex/score.lock.test.ts:27` / `tests/fixtures/score-lock.json`
**Problem**: The test compares output only with `versions[ENGINE_VERSION]`. A developer who changes scoring and regenerates entry `"1"` in place, instead of bumping, gets a green run. Nothing pins the frozen entries. The rule "never edit an older entry" lives only in comments.
**Why it matters**: AC-4's purpose is that stored `engineVersion` values tell you which rules made a number. A silently rewritten v1 breaks that, and every saved result then claims the wrong rules.
**Suggested fix**: Pin a hash of each version's entry in the test source, for example `{ "1": "sha256:..." }`, so changing a frozen entry needs an obvious, reviewable edit in two places. Or add a CODEOWNERS / review rule on the fixture. This is cheap and makes the lock real.

### 🟡 A sign in race can briefly draw another account's server result, `src/lib/session.ts:629`
**Problem**: Page scripts start after 700 ms while `verify()` may still be running. If the cookie now belongs to account B but the cache is A's, `loadResult` captures A's cache, and `mine` (authenticated as B) returns B's result. The write guard (`authUserId === cache.owner`) correctly skips saving it. The page still draws B's numbers with A's cached profile, until the guard's post verify `location.reload()`.
**Why it matters**: The window is narrow and both accounts were on the same device, but it mixes one student's result with another's name. The wipe on account change exists to prevent exactly this.
**Suggested fix**: After the server answers, resolve only if `authUserId === cache.owner`. Otherwise treat it as "redirected/reloading" and return null.

### 🟡 No unit test covers the browser bridge's `result()` / `loadResult` / `flatten` logic
**Problem**: The decision order (AC-14), `flatten`, the `not_completed` path and the retry box are covered only by e2e tests against the dev deployment, and none of them covers the timer and retry interleavings (see the Major above).
**Suggested fix**: Add a jsdom unit test with a mocked client for `flatten`'s refusals, the owner checks in `readResultCopy`, and the retry sequence.

## Strengths
- `makeResult` gets the transaction semantics right. It runs inside the same mutation as `completedAt`, uses `findResult` by index first (so OCC serialises concurrent `complete` / `ensure`), wraps only the engine call, and refuses to save unless exactly 18 answers were scored. The `complete` early return also repairs pre-release checks.
- Flags are isolated well: a separate table, `splitResult` keeps them out of `detail`, and `results.test.ts` scans the sources to enforce no patch/delete, inserts only in `resultsCore.ts`, `resultFlags` touched only by two files, and no result field in the Sheet code. AC-8, AC-5 and AC-11 are encoded as tests, not just comments.
- The server runs the browser's own `score.js` (no second copy), and AC-2 is checked field for field.
- Removing `score.js` and `questions.js` from challenge and leaderboard is safe: neither page script uses `DhiQuestions` or `DhiScore`, done and who keep `questions.js`, and the e2e asserts no `pageerror` on those pages.
